# XBed 玄剑起床战争赛事平台
## S1 项目级产品需求与技术开发规格书

**项目名称：** XBed  
**项目定位：** 玄剑公会起床战争赛事管理与竞技档案平台  
**开发组织：** 北域工作室 Northland Studio  
**身份认证：** 玄剑官网 OAuth 2.0  
**网站地址：** `https://xbed.xuanjian.top`  
**部署方式：** 与玄剑官网共用物理服务器，独立应用部署

**目标版本：** S1

# 第一部分：项目概述

## 1.1 项目背景

玄剑公会是一个长期运行的 Minecraft 玩家自治社群。随着公会传统大型基建活动的组织成本增加，成员在线时间逐渐分散，需要一种参与门槛较低、单次活动时间较短、能够持续维持成员互动的竞技活动。

XBed 是玄剑公会起床战争竞技赛事平台。

通过将公会闲置游戏服务器改造为起床战争竞技服务器，以赛季积分、个人竞技档案、段位、排行榜和赛事管理制度，形成可持续运行的线上竞技活动。

XBed 不只是一个战绩展示网站，而是玄剑公会内部的一项制度实验。

其设计必须遵循玄剑公会既有组织治理原则，不得擅自改变玄剑公会的组织根本规则。

## 1.2 项目目标

1. 建立独立的 XBed 赛事门户。
2. 通过玄剑 OAuth 2.0 实现统一身份认证。
3. 建立完整的赛季、比赛、报名和参赛资格管理系统。
4. 接入实际运行的 Minecraft 起床战争服务器。
5. 自动采集服务器比赛数据。
6. 建立服务器数据、玩家日志和 ReplayMod 回放的交叉核验机制。
7. 建立人工赛果审核和申诉机制。
8. 建立独立的赛事积分、段位和排行榜。
9. 建立长期个人竞技档案。
10. 提供完整的赛事管理后台。
11. 保证赛事原始数据和管理操作可追溯。

## 1.3 S1 范围约束

S1 必须优先完成完整的单服务器赛事闭环。

不应为了未来可能出现的需求而引入过度复杂的架构。

以下内容暂不纳入 S1：

- 多游戏服务器接入。
- 战队与比赛队伍的关联。
- 战队积分及战队排行榜。
- 贡献点交易、发放、扣除和兑换。
- 贡献点竞猜或押注。
- 游戏商城、皮肤购买及服务器经济系统。
- 外部玩家特邀参赛机制。
- 英文语言包。
- 游戏服务器远程控制。
- 独立 ELO 评分系统。
- 独立的第二套锦标赛积分体系。

# 第三部分：玄剑 OAuth 2.0 身份认证

## 3.1 认证原则

XBed 不建立独立的账号密码登录体系。

所有用户通过玄剑官网 OAuth 2.0 登录。

OAuth 文档：

`https://github.com/northland-studio/xuanjian.top/blob/master/docs/OAUTH.md`

开发时必须重新检查该文档和官网实际接口实现，以最新代码为准。

不得仅依据本规格书中的接口摘要推断实际参数。

## 3.2 OAuth 接入模式

使用机密客户端 Authorization Code Flow。

XBed 需要在玄剑官网登记独立 OAuth 客户端。

配置：

- `client_id`
- `client_secret`
- `redirect_uri`
- `allowed_scopes`

`client_secret` 只能保存在服务端环境变量或安全配置中，不得进入浏览器代码、前端构建产物或 Git 仓库。

申请 Scope：

- `read:user`
- `read:member`

OAuth 文档中涉及的主要接口包括：

- `/api/oauth/authorize`
- `/api/oauth/token`
- `/api/oauth/revoke`
- `/api/oauth/verify`
- `/api/oauth/userinfo`
- `/api/oauth/member`
- `/api/oauth/scopes`

具体参数、请求方式和响应结构必须以最新 OAuth 文档为准。

## 3.3 登录流程

1. 用户访问 XBed。
2. 用户点击玄剑账号登录。
3. 跳转至玄剑 OAuth 授权页面。
4. 用户完成授权。
5. 玄剑返回授权码。
6. XBed 服务端使用授权码和机密客户端凭据交换 Token。
7. 服务端验证 Token。
8. 获取用户资料和成员身份。
9. 检查成员资格及等级。
10. 创建或更新 XBed 本地用户记录。
11. 建立 XBed 登录会话。

必须严格验证：

- `state`
- `redirect_uri`
- 授权码有效性
- Token 有效性
- OAuth 返回的用户身份
- Scope 授权范围

正确实现 Refresh Token 轮换机制。

不得在前端暴露 Client Secret 或长期有效的敏感 Token。

## 3.4 用户参赛资格

S1 仅允许玄剑公会成员。

登录时必须满足：

`is_member = true`

不允许普通游客注册 XBed 账号，也不开放外部玩家特邀注册。

成员资格校验只在 OAuth 登录时执行。

特别注意：

- 用户登录时属于玄剑成员，即可建立 XBed 当前登录态。
- 用户登录后退出玄剑公会，不主动取消当前 XBed 登录态或赛事资格。
- 不进行定期成员资格检查。
- 不在每次业务请求中重新校验成员资格。
- 用户下一次重新登录时，才重新检查成员资格。
- 历史竞技档案永久保留。

不得擅自将成员资格检查改成实时检查或定期检查。

## 3.5 用户资料同步

每次 OAuth 登录成功后同步：

| 字段 | 来源 |
|---|---|
| 玄剑用户 ID | OAuth |
| 用户名 | OAuth |
| 昵称 | OAuth |
| 头像 | OAuth |
| 等级 level | OAuth |
| 称号 title | OAuth |
| 贡献点 contribution | OAuth |
| 是否公会成员 | OAuth |
| 游戏 ID | OAuth |

玄剑用户 ID 是 XBed 外部身份关联的唯一标识。

昵称变化不得影响历史比赛记录。

上述玄剑资料由官网管理，XBed 不允许用户自行修改。

`level=-1` 的托管系统账号不得进入普通 XBed 用户体系。

## 3.6 贡献点只读接入

XBed 通过 OAuth 的 `read:user` Scope 获取贡献点信息。

允许：

- 展示贡献点余额。
- 在个人中心展示贡献点资料。

不允许：

- 发放贡献点。
- 扣除贡献点。
- 贡献点转账。
- 贡献点兑换赛事积分。
- 贡献点竞猜或押注。
- 建立独立贡献点账本。

XBed 竞技积分与玄剑贡献点是两个完全独立的体系。

## 3.7 用户邮箱

OAuth 返回资料不包含邮箱，不得假定可以同步邮箱。

用户首次登录后需要在 XBed 独立填写邮箱，并完成邮件验证码验证。

要求：

- 邮箱与玄剑 OAuth 用户 ID 关联。
- 邮箱不作为登录账号。
- 邮箱不向其他玩家公开。
- 用户可以更换邮箱。
- 更换邮箱必须重新验证。
- 验证码应有有效期和发送频率限制。
- 邮箱验证完成前不能报名参赛。
- 已获得参赛资格的玩家更换邮箱期间，不自动取消资格。

# 第五部分：赛季与赛事体系

## 5.1 赛事定位

赛事名称暂定：

**XBed 玄剑起床战争挑战赛 S1**

XBed S1 是玄剑公会内部竞技制度实验。

S1 仅面向玄剑成员。

暂不开放外部特邀机制。

## 5.2 赛季机制

赛季长度不固定。

由超级管理员创建和配置赛季。

每个赛季应具有：

- 赛季名称。
- 赛季编号。
- 赛季介绍。
- 开始时间。
- 结束时间。
- 赛季状态。
- 报名状态。
- 初始积分。
- 最低积分限制。
- 胜负积分规则。
- 段位规则。
- 奖励政策相关配置。
- 创建时间。
- 修改记录。

赛季结束时自动封存：

- 冻结最终积分。
- 冻结最终排名。
- 生成最终排行榜。
- 保留历史赛事记录。
- 禁止常规成绩修改。
- 保留赛季配置版本。

赛季封存后不得随意修改历史成绩。

## 5.3 比赛组织方式

S1 支持两种比赛组织方式：

### 自由开赛

玩家在服务器正常参与起床战争。

服务器插件自动识别符合条件的正式比赛并上报。

### 管理员组织

管理员可以组织指定比赛。

可以设置实际服务器插件支持的比赛模式、时间及参赛要求。

两种组织方式共用同一套积分、赛果审核、个人档案和排行榜体系。

不得建立独立锦标赛积分体系。

## 5.4 比赛模式与人数

比赛模式、地图、队伍人数和具体参赛人数限制，必须根据服务器实际运行的起床战争核心插件能力确定。

不得在不了解插件实际支持能力的情况下预先假定某种比赛模式可用。

由 DSH 检查服务器插件后制定具体支持列表。

## 5.5 统一积分规则

所有正式比赛执行统一规则：

| 比赛结果 | 积分变化 |
|---|---:|
| 胜利 | +5 |
| 失败 | -5 |
| 平局 | 0 |

不允许：

- 特殊比赛积分翻倍。
- 自定义积分倍率。
- 管理员临时改变单场积分。
- 通过锦标赛身份给予额外积分。

积分规则属于赛季统一规则。

## 5.6 比赛次数

不设置每日比赛次数限制。

不设置赛季累计比赛次数限制。

所有符合赛事规则且审核通过的比赛均正常计入统计和积分。

保留比赛场次及时间记录，供管理后台进行异常分析。

## 5.7 报名系统

报名采用基础必填字段 + 赛季自定义字段的结构。

基础数据结构必须保持统一。

赛季管理员可以增加适合当前赛季的自定义报名字段。

报名满足参赛资格和表单校验后立即生效，不进行人工逐个审核。

管理员仍然可以处理特殊违规、取消资格和名单调整。

报名成功后获得该赛季参赛资格。

参加该赛季符合条件的比赛不需要每场重复报名。

## 5.8 排名机制

排行榜排序：

1. 总积分降序。
2. 胜率降序。
3. 总击杀数降序。
4. 三项仍相同则并列排名。

胜率根据有效比赛场次计算。

未参赛用户不参与胜率比较。

每场赛果审核通过后立即更新排行榜。

公开排行榜和管理后台数据必须保持一致。

## 5.9 奖励制度

具体赛季奖励由玄剑公会管理组决定。

XBed 提供必要的奖励配置、奖励展示及发放记录能力，但不得自行制定公会奖励政策。

不得擅自将奖励与贡献点绑定。

# 第六部分：段位系统

## 6.1 积分决定段位

采用积分区间直接划分段位。

不使用独立 ELO 评分。

赛季积分与赛季段位联动。

## 6.2 双段位体系

设置：

1. 永久历史段位。
2. 当前赛季段位。

赛季段位根据当前赛季积分计算，每个新赛季重新开始。

永久历史段位根据长期累计竞技积分形成，作为长期竞技荣誉。

两种段位都采用积分区间决定。

## 6.3 段位管理

超级管理员可以：

- 创建段位。
- 删除段位。
- 调整段位排序。
- 设置段位名称。
- 设置积分门槛。
- 设置图标。
- 设置颜色。

历史段位和赛季段位规则分别管理。

段位规则修改时保留历史版本，避免历史档案被意外改变。

# 第七部分：玩家个人竞技档案

## 7.1 个人档案内容

完整个人档案至少包含：

### 基础信息

- 玄剑昵称。
- 头像。
- 用户名。
- 游戏 ID。
- 公会等级。
- 公会称号。
- 贡献点余额（只读）。

### 竞技数据

- 总场次。
- 胜场。
- 败场。
- 平局。
- 胜率。
- 总击杀。
- 总死亡。
- 赛季积分。
- 当前段位。
- 永久历史段位。

### 历史记录

- 历届赛季排名。
- 历届赛季积分。
- 历届参赛记录。
- 历史段位变化。
- 比赛历史。
- 比赛结果。
- 比赛队伍。
- 地图。
- 个人比赛表现。

### 最佳纪录

- 最高单场击杀。
- 最长连胜。
- 最佳胜率。
- 其他能够由实际数据可靠计算的记录。

### 数据分析

- 胜负趋势。
- 击杀趋势。
- 赛季表现图表。
- 个人竞技数据变化。

## 7.2 数据来源

个人档案数据必须来源于正式审核通过的比赛结果。

未经审核的服务器原始数据不得直接进入正式统计。

## 7.3 玩家可见范围

玩家可以查看公开赛事结果、自己的正式成绩和公开排行榜。

不得向普通玩家展示：

- 服务器原始比赛数据。
- 其他玩家的原始 `latest.log`。
- 其他玩家的 `.mcpr` 文件。
- 完整管理员审核过程。
- 私有审核材料。

玩家不能直接访问原始证据文件。

## 8.1 S1 功能范围

- 移除成员。

- 是否允许创建战队。

- 战队最高人数。

# 第九部分：服务器插件与比赛数据采集

## 9.1 基本原则

服务器插件必须根据实际运行环境开发。

不得预先假定服务器使用 BedWars1058 或其他特定起床战争核心。

DSH 必须自行嗅探服务器实际环境。

## 9.2 插件嗅探任务

开发前检查：

1. Minecraft 服务端类型及版本。
2. Paper 及其兼容情况。
3. 服务器插件列表。
4. 起床战争核心插件名称。
5. 核心插件版本。
6. 插件依赖。
7. 插件公开 API。
8. 插件事件系统。
9. 比赛生命周期。
10. 玩家统计接口。
11. 队伍与地图接口。
12. 胜负判定机制。
13. 现有统计数据来源。
14. 是否能够获取单场比赛统计。

如果可以获取插件源码，应优先检查实际实现。

输出完整的插件能力分析报告。

## 9.3 数据采集策略

优先使用起床战争核心插件提供的 API 和事件。

如果核心插件没有提供必要的数据，可以根据实际情况监听 Paper 或 Minecraft 底层事件进行补充。

是否补充、补充哪些事件，由 DSH 根据可靠性、开发成本和实际必要性决定。

禁止为了追求数据全面而进行不必要的复杂开发。

不能可靠获取的数据必须明确标记为不支持，不得伪造。

## 9.4 数据契约

最终 API 数据契约必须根据实际插件嗅探结果制定。

至少研究以下数据类别：

- 比赛唯一标识。
- 比赛地图。
- 比赛模式。
- 比赛开始时间。
- 比赛结束时间。
- 玩家 UUID。
- 玩家游戏 ID。
- 玩家所属队伍。
- 玩家最终排名。
- 比赛胜负。
- 击杀数。
- 死亡数。
- 最终击杀数。
- 最终死亡数。
- 床摧毁数据。
- 玩家加入和退出。
- 玩家重连。
- 队伍淘汰。
- 比赛结束原因。
- 可用的其他核心插件统计。

以上是调查目标，不代表所有字段都已确认可以获取。

必须形成：

1. 插件事件映射表。
2. 数据字段映射表。
3. 不支持字段列表。
4. 单场比赛数据采集方案。
5. 比赛异常处理方案。
6. API 契约文档。

注意：部分插件可能只提供累计统计，不能直接将累计值当作单场统计。

## 9.5 比赛 ID

比赛 ID 的生成方式由 DSH 自行设计。

要求：

- 全局唯一。
- 生成后稳定。
- 同一场比赛重试时始终使用同一个 ID。
- 防止重复创建。
- 防止重复审核。
- 防止重复结算积分。
- 明确服务器身份和比赛 ID 的关联。

不强制预先采用某一种 UUID 或数据库 ID 方案。

## 9.6 单服务器约束

S1 仅支持一台比赛服务器。

不开发多服务器管理功能。

服务器拥有独立身份和 API 密钥。

# 第十部分：服务器 API 安全与可靠性

## 10.1 通信方向

采用服务器主动推送模式。

游戏服务器插件向 XBed API 发送比赛数据。

XBed 不主动查询游戏服务器。

不提供：

- 远程开始比赛。
- 远程结束比赛。
- 远程踢出玩家。
- 远程修改游戏规则。
- 远程控制服务器。

## 10.2 HMAC-SHA256 认证

服务器使用独立密钥进行 HMAC-SHA256 请求签名。

每次请求至少包含：

- 服务器身份标识。
- 时间戳。
- 请求唯一标识 Nonce。
- 请求签名。
- 请求内容。

签名必须覆盖约定的请求方法、路径、时间戳、Nonce 和请求体摘要等关键内容。

具体规范由 DSH 制定并形成 API 文档。

必须实现：

- 时间戳有效窗口校验。
- Nonce 唯一性校验。
- 重放攻击防护。
- 请求体完整性校验。
- HTTPS 强制通信。
- 密钥安全保存。
- 密钥轮换。
- 密钥吊销。
- 签名失败审计。

不得将密钥硬编码进公开仓库。

## 10.3 自动重试

选择自动重试机制。

服务器插件必须在本地持久化保存待上报比赛数据。

上报失败后：

1. 保留原始待发送数据。
2. 自动重试。
3. 网络恢复后继续发送。
4. 使用原始比赛 ID。
5. 收到明确成功响应后标记为已上报。
6. 长期失败的数据必须能够被管理员发现。

不能因为服务器重启、网络断开或 XBed 暂时不可用而丢失比赛数据。

重试策略、退避时间和本地队列实现由 DSH 自行设计。

## 10.4 上报幂等性

服务器插件重复上报同一比赛时，XBed 不得重复创建比赛记录。

同一比赛不得重复生成正式赛果或重复结算积分。

## 10.5 数据上报接口

必须形成完整 REST API 契约，包括：

- 接口地址。
- HTTP 方法。
- 认证方式。
- 请求头。
- 请求体。
- 响应体。
- 错误码。
- 签名规则。
- 幂等规则。
- 重试规则。
- 数据版本兼容策略。

所有接口必须提供实际可运行的联调示例。

# 第十一部分：比赛异常处理

## 11.1 异常检测

出现以下情况时，应根据实际可检测能力标记异常：

- 服务器崩溃。
- 比赛异常终止。
- 关键比赛数据缺失。
- 比赛生命周期不完整。
- 数据冲突。
- 比赛状态无法确认。

## 11.2 异常比赛规则

异常比赛：

- 自动标记为异常。
- 不进入正式积分结算。
- 不进入正式排行榜。
- 保留已采集原始数据。
- 保留玩家上传材料。
- 后台显示异常原因。

不自动恢复比赛。

不自动判断胜负。

## 11.3 异常比赛裁定

由管理员决定最终处理方式：

### 判定有效

经补充核验后，允许纳入正式赛果。

### 判定无效

不计入正式赛事统计。

### 安排重赛

组织新的比赛。

原异常比赛保留为历史记录。

所有裁定必须记录操作者、时间、理由和最终结果。

# 第十二部分：比赛赛果与证据管理

## 12.1 自动生成审核草稿

服务器上报成功后，XBed 自动生成待审核比赛记录。

流程：

1. 接收服务器数据。
2. 验证 HMAC 签名。
3. 验证数据格式。
4. 检查比赛 ID。
5. 保存服务器原始数据。
6. 创建比赛审核草稿。
7. 关联参赛玩家。
8. 关联玩家日志和回放提交状态。
9. 展示数据完整性。
10. 等待管理员审核。

服务器上报成功不代表正式赛果生效。

## 12.2 玩家日志

每场比赛每位参赛玩家都必须上传自己的 Minecraft `latest.log`。

截止时间：

**比赛结束后 1 小时内。**

后台必须记录：

- 上传者。
- 比赛 ID。
- 文件大小。
- 上传时间。
- 是否逾期。
- 是否缺交。
- 文件完整性。
- 审核关联关系。

未提交日志时，该玩家成绩暂不正式生效。

逾期或缺交不自动判定无效，由管理员结合服务器数据、录像和其他玩家证据裁定。

`latest.log` 永久保留。

## 12.3 ReplayMod 回放

每位参赛玩家都必须上传自己的 ReplayMod `.mcpr` 文件。

截止时间：

**比赛结束后 1 小时内。**

文件必须关联：

- 比赛 ID。
- 玩家身份。
- 玄剑 OAuth 用户 ID。
- 上传时间。
- 文件大小。
- SHA-256 校验值。

不得把 `.mcpr` 当成普通视频文件处理。

必须保留原始回放，不允许覆盖。

## 12.4 文件存储

S1 文件保存在 XBed 服务器本地磁盘。

不接入第三方对象存储。

文件与业务数据库分离存储。

要求：

- 随机文件名。
- 私有文件目录。
- 文件类型校验。
- 文件大小限制。
- 文件访问鉴权。
- SHA-256 完整性校验。
- 上传状态管理。
- 存储空间统计。
- 后台文件管理。
- 上传异常处理。

文件名不得直接使用用户提供的文件名作为磁盘存储路径。

## 12.5 文件保留期限

| 文件 | 保留期限 |
|---|---|
| `.mcpr` | 所属赛季结束后统一清理 |
| `latest.log` | 永久保留 |
| 正式赛果 | 永久保留 |
| 审核记录 | 永久保留 |
| 积分变更记录 | 永久保留 |
| 申诉记录 | 永久保留 |

赛季清理 `.mcpr` 时：

- 保留正式赛果。
- 保留比赛统计。
- 保留审核结论。
- 保留审计记录。
- 记录清理执行时间。
- 记录清理文件数量。

## 12.6 证据审核工作台

管理后台必须提供完整证据工作台。

至少包括：

### 服务器原始数据

展示服务器提交的原始数据、比赛基本信息和玩家统计。

### 玩家日志

展示每位玩家的 `latest.log` 提交状态、时间和逾期情况。

### ReplayMod 回放

展示每位玩家 `.mcpr` 文件信息，并提供有权限的管理员下载入口。

### 比赛事件时间线

展示实际能够获取的比赛事件。

例如：

- 击杀。
- 死亡。
- 床摧毁。
- 玩家退出。
- 玩家重连。
- 队伍淘汰。

具体事件以实际插件支持能力为准。

### 数据交叉对比

展示服务器数据与玩家日志之间的差异。

### 异常提示

包括：

- 材料缺交。
- 数据冲突。
- 回放损坏。
- 文件校验失败。
- 比赛异常终止。
- 其他可以可靠识别的问题。

### 修正记录

展示赛果修改前后数据、修改人、时间及理由。

# 第十三部分：赛果审核

## 13.1 审核权限

L1 管理员和 L2 超级管理员拥有相同的独立赛果审核权。

不设置初审、终审两级流程。

不要求双人会签。

任意具备审核权限的管理员均可：

- 审核通过。
- 驳回。
- 修正赛果。
- 处理相关证据。
- 提交审核意见。

## 13.2 审核流程

建议状态：

1. 待审核。
2. 审核中。
3. 驳回待补充。
4. 重新提交。
5. 审核通过。
6. 异常待裁定。
7. 已裁定。
8. 已作废。

状态变化必须记录。

## 13.3 审核驳回

允许管理员驳回赛果。

驳回必须填写理由。

驳回后允许：

- 补充材料。
- 重新核验。
- 修正草稿。
- 再次提交审核。

保留每次审核意见和历史版本。

## 13.4 赛果修改

管理员可以在审核过程中直接修改自动生成的赛果草稿。

可修改实际支持的：

- 胜负结果。
- 击杀数。
- 死亡数。
- 其他玩家统计。
- 其他比赛统计。

必须填写修改理由。

服务器原始数据和玩家原始材料不可覆盖。

记录修改前后数据。

## 13.5 正式生效

只有审核通过后才可以：

- 生成正式赛果。
- 结算积分。
- 更新排行榜。
- 更新个人竞技档案。
- 触发通知。

## 13.6 审核冲突

不设置专门的管理员审核冲突机制。

以最先完成的有效审核结果为准。

后续认为赛果有误时，通过既有申诉或纠错流程处理。

7. 积分不得重复结算。
